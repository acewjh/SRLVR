## 3. 关于"GRPO 比 SRLVR 高 0.08"的判读

### 这不是算法差异，是采样口径差异

两臂的**预算是严格匹配的**：每个优化步都是 32 条真实轨迹。但任务采样方式完全不同：

| | 每轮不同任务数 | 每任务重复 | 每轮轨迹 |
|---|---|---|---|
| SRLVR（G=1） | **32** | 1 | 32 |
| GRPO（bs=4 × G=8） | **4** | 8 | 32 |

所以 SRLVR 的单轮 success_rate 是 **32 个任务的平均**，GRPO 的是 **4 个任务的平均**。20 轮下来，SRLVR 见过 640 个不同任务，GRPO 只见过 80 个。

**证据一：方差。** GRPO 的标准差是 SRLVR 的两倍多（8B：0.110 vs 0.052；4B：0.102 vs 0.080），完全符合"样本量少 8 倍"的预期。

**证据二：在 4B 上同样复现。** 你自己的 4B 实验里，GRPO 0.868 vs SRLVR batch 0.784，差 0.084 —— 与 8B 的 0.076 同向同量级。这说明它不是 8B 的产物，而是两种配置的系统性差异。

**证据三：GRPO 频繁打满。** 8B GRPO 有 7/20 轮 success_rate 恰好 1.0，4B GRPO 是 22%。4 个任务全部成功并不罕见；32 个不同任务全部成功则几乎不可能——所有 SRLVR 臂（G=1×32）的这个比例都是 0%。

**结论：这两个数不能直接比。** 要做公平对比，必须让两臂采样同样数量的不同任务（例如 GRPO 用 bs=32 × G=1，或 SRLVR 用重复采样），或者在固定的评测集上离线评测两个 checkpoint。

### 一个顺带发现：GRPO 的零梯度步随规模恶化

GRPO 的 advantage 要除以组内奖励标准差，组内全对则标准差为 0 → **advantage 恒为 0 → 这些优化步完全没有梯度信号**。

| 臂 | success_rate==1.0 的轮占比 |
|---|---|
| 8B GRPO | **35%**（7/20） |
| 4B GRPO | **22%**（5/23） |
| 4B GRPO-rpp | 5%（2/41） |
| 1.7B GRPO-rpp | 0% |
| 所有 SRLVR 臂（G=1×32） | **0%** |

8B GRPO 名义上的 20 步，实际只有 13 步在训练。**在接近饱和的任务上，GRPO 的有效样本效率随成功率上升而塌缩，且随模型规模单调恶化**——这比 success_rate 更值得关注。SRLVR 的 G=1×32 结构天然不受此影响，因为 32 个不同任务不会同时全对。

## 4. 效率：完整的时间账

### 4.1 批大小（容易被误读）

| 层级 | SRLVR | GRPO |
|---|---|---|
| 每轮真实轨迹 | 32（G=1 × 32） | 32（bs=4 × G=8） |
| `GBS_OVERRIDE` 请求 | 32 | 32 |
| **slime 实际 `global_batch_size`** | **728 ~ 916 行（动态）** | 同量级 |
| `micro_batch_size` | 1 | 1 |
| 每轮优化步 | 1 | 1 |

v2 协议**按 turn 训练**：32 条轨迹展开成约 900 个 turn，每个 turn 一行。所以一个优化步吃 **91 万个带梯度的 token（完整前向 257 万）**。

### 4.2 单轮耗时（SRLVR rollout 11 实测）

| 段 | 耗时 | 占比 |
|---|---|---|
| **采样** | ~54 min | 54% |
| 参考 logprobs | 220 s | 4% |
| 后见打分（SRLVR 特有） | 832 s | 14% |
| **标定探针（4 个）** | **938 s** | **16%** |
| actor 前向+反向 | 772 s | 13% |
| 训练小计 | 46 min | 46% |
| **合计** | **~100 min** | |

实际整体：**SRLVR 21 轮用 28 小时（80 分钟/轮）；GRPO 20 轮用 17 小时（51 分钟/轮）**。GRPO 快 36%，因为没有后见打分和标定探针这两段（合计占 SRLVR 训练段的 64%）。

### 4.3 吞吐

| 指标 | 值 |
|---|---|
| `perf/tokens_per_gpu_per_sec` | 50 – 75 |
| 并发倍数（`generation_seconds_sum / episode_wall_seconds_max`） | **8.7** |
| SGLang `max_running_requests` | 8/引擎 × 4 引擎 = 32 |
| KV 池峰值使用率 | **0.33**（67% 闲置） |
| `rollout/environment_seconds_sum` | 318 s（**仅占生成的 1.1%**） |

并发已生效（加 `ALFWORLD_ENV_ACTORS=1 ALFWORLD_ENV_WORKERS=32` 之前 `#running-req` 全程 0/1，之后升到 8，采样段从 72 分钟降到 ~54 分钟）。环境侧和显存都不是瓶颈。

## 5. 最重要的效率发现：失败轨迹吃掉一半算力

统计 SRLVR 臂全部 **416 条 episode**：

| | 条数 | turns 中位数 | 生成耗时中位数 |
|---|---|---|---|
| 成功 | 347 (83.4%) | 13 | 279 s |
| 失败 | 69 (16.6%) | **全部恰好 50**（超时） | 1979 s |

**每一条失败都是撞上 `MAX_TURNS=50` 的超时，没有一条是中途判负。** 失败轨迹平均耗时是成功的 7 倍。

> 总生成 77.9 小时中，**37.1 小时（47.7%）花在这 16.6% 的超时轨迹上。**

这解释了采样段为什么是 54 分钟：`episode_wall_seconds_max` = 3261 s，拖后腿的就是这些超时轨迹，平均轨迹只要 888 s。**采样被单条最慢轨迹锁死，不是吞吐不够。**

成功轨迹的 turns 分位数：`p50=13  p75=23  p90=35  p95=40  p99=47`

| MAX_TURNS | 损失的成功轨迹 | 省下的生成时间 |
|---|---|---|
| 40 | 4.6% | 9.5% |
| **35** | **8.4%** | **14.3%** |
| 30 | 14.7% | 19.1% |
| 25 | 21.9% | 23.9% |

**建议下个 campaign 用 `MAX_TURNS=35`。** 改了就与当前这组（50）不可比，所以我们没有在进行中的实验里动它。

## 6. 异步 / continuous rollout：在这个任务上不能用

slime 支持（`--partial-rollout`、`--over-sampling-batch-size`、`--dynamic-sampling-filter-path`），`over_sampling_batch_size` 在 `methods/hsi_rollout.py:478` 已被读取，只是默认等于 `rollout_batch_size`。

**但实测否决了这条路**，基于同样那 416 条 episode：

```
按生成耗时排序：
  最快的 2/3 (n=277)  成功率 = 1.000
  最慢的 1/3 (n=139)  成功率 = 0.504
```

异步/over-sampling 的做法是"多生成一些，谁先跑完就用谁"。在 ALFWorld 上**先跑完的几乎全是成功轨迹**，取先完成的 32 条会得到接近 100% 成功率的批次 → **奖励方差塌缩到 0 → advantage 恒为 0 → 训练静默变成 no-op**，而 `grad_norm` 看起来完全正常。

（这与 §3 里 GRPO 组内全对导致零梯度是同一个机制，只是触发方式不同。）

第二个障碍：`--partial-rollout` 回收未完成样本的设计意图是**续写 token**；ALFWorld 的未完成 episode 需要 Ray actor 里的**环境状态**活到下一轮，`methods/` 里没有代码处理这件事。

## 7. 还能安全提速的只有一处

**标定探针 4 → 2，省约 8 分钟/轮（−8%），数学上完全等价。**

依据 `methods/srlvr_hsi.py:849`：

```python
actor_lam = 0. if cfg.actor_lambda_zero else lam
```

λ=0 臂里探针算出的 `lambda_calibrated`（实测 0.225）**根本不会进 actor**，那 938 秒是纯诊断。代码要求 `2 <= probes`，所以 2 是下限。建议你后续的 λ=0 消融臂直接用 `SRLVR_CALIBRATION=2`。

### 已排除的提速方向（都有实测依据）

| 方向 | 结论 |
|---|---|
| 序列打包 / `use_dynamic_batch_size` | SRLVR 要求 `micro_batch_size==1` 且显式拒绝 dynamic batch |
| 提高并发 | 已匹配：32 条轨迹 / 32 env worker / 4 引擎 × 8 并发。上不去是长尾所致 |
| 推理侧 TP=2 / 降 `mem_fraction` | KV 池峰值使用率仅 0.33，显存不是瓶颈 |
| `padded_tokens` 看似 2.8 倍浪费 | **误读**。`actor_tokens` 只统计 loss mask 内的 token，`padded_tokens` 是完整序列长度，差额主要是 prompt（必须前向） |

## 8. 8B 适配：改了什么

| # | 问题 | 性质 | 修复 |
|---|---|---|---|
| 1 | 本机无 conda 环境 `PyTorch-2.9.0` | 环境 | `npu_env.sh` 增加 `OPSD_VENV` 支持 |
| 2 | `npu_env.sh` 硬编码 `cann-8.5.1`，本机不存在 | 环境 | 按优先级探测，并**打印选中项** |
| 3 | `BASE`/`PROJ` 硬编码路径，副本代码不被加载 | 环境 | 改为 `CUA_PROJ`/`CUA_BASE` 可覆盖 |
| 4 | sglang 默认 grammar backend 需要 `xgrammar` | 环境 | 缺失时降级为 `none` |
| 5 | **`MAX_RESPONSE=128` 导致 100% 截断** | **8B 规模** | 改为 4096 |
| 6 | **全参数 8B 的 DDP 缓冲 OOM** | **8B 规模** | TP=4 + 梯度重建改用 `all_gather_into_tensor` |

### 8.1 `MAX_RESPONSE=128` 会让训练静默变成 no-op

`run_alfworld_v2_grpo_8b.sh` 里写的是 128。实测：

```
truncated_ratio   = 1.0     每条响应都撞上限
action_valid_rate = 0.0     动作解析不出来
success_rate      = 0.0     reward 恒为 0
```

reward 全 0 → advantage 恒 0 → **没有梯度信号，但 `grad_norm` 看起来正常**。改成 4096 后 `0.0 → 0.844`。

**建议**：修正那个 launcher 的 128，并在 `_common_v2.sh` 加启动后校验——首个 rollout 后若 `truncated_ratio > 0.9` 直接失败退出。

### 8.2 全参数 8B 的显存

```
权重 bf16 16.4 GB + 梯度 bf16 16.4 GB = 32.8 GB 在卡上，按 TP 切分
AdamW fp32 m+v 65.6 GB → CPU offload（默认已开）

TP=1   32.8 GB/卡                      → OOM
TP=2   两块扁平 DDP buffer 各 15.26 GiB  → 30.5 > 29.49，OOM
TP=4   7.63 GiB/块                     → 可行
```

Megatron 的 DDP 会分配 **param buffer 和 grad buffer 两块扁平连续内存**，这是 TP=2 装不下的直接原因——不是激活。

TP=4 等价性在放宽前已验证：分片词表打分 vs dense，2/4/8 分片 `dloss=3.73e-08`、hidden 梯度相对误差 ~7e-07。你 15:41 的更新已把限制改成 `tp >= 1`，方向一致。

### 9.1 最值得合的一条

```python
# methods/srlvr.py::_reconstruct_dp_gradients
# 原实现：bucket 之外还要约 2 倍空间
local = bucket.grad_data.chunk(dp)[rank].contiguous()
pieces = [torch.empty_like(local) for _ in range(dp)]
dist.all_gather(pieces, local, group=group)
bucket.grad_data.copy_(torch.cat(pieces))

# 改为：峰值降到单份 local，算术完全等价
local = bucket.grad_data.chunk(dp)[rank].clone()
dist.all_gather_into_tensor(bucket.grad_data, local, group=group)
del local
```

8B 全参数下原实现是 7.63 GiB 的单次分配。三次 OOM（`srlvr8b-v2-02` / `cap-probe` / `v2-05`）都发生在**总量够但单次分配过大**的时候。`grad_data` 本就是 `dp × local.numel()`，rank 序拼接，等价性无疑问。

### 9.2 顺带发现的小问题

1. `methods/tp_utils.py` 里 `def tp_sum` **定义了两次**（后者覆盖前者，逻辑相同）——笔误。
2. `opsd_core/experiment_metrics.py:25` import `methods.srlvr_hsi`——L0 → L1 分层违规，`tests/test_opsd_core.py` 的 AST 检查会报。
3. `verify_dp_capture` 调用 `capture_full_gradient` 的**闭包局部函数** `_tp_full_grad` 会抛 `NameError`（我们这边改成内联了）。

### 9.3 留给 v4 的提醒

我们写过一个 v4 的 TP 等价性测试，**它的自检失败了**：测试里模拟 `tp_sum_shared`（反向也 all-reduce）和 `tp_sum(differentiable=True)`（pass-through 反向）的两个类，`backward` 写成了一样，所以**无法区分两种语义**，对已知的 49% 梯度 bug 完全瞎。单进程模拟分片时 autograd 会自动正确累加跨分片梯度，掩盖了真实分布式下 pass-through 丢失其他 rank 偏导的问题。

要做 v4 的 TP 验证，必须模拟"每个 rank 只拿到自己那份梯度"。你已把 v4 限制改成 `tp >= 1`，如果还没做过这类验证建议补一个——**这个 bug 在 loss 和 grad_norm 上都看不出来**。


### 执行过程中的两个瑕疵（如实记录）

1. **GRPO 在第 10 轮被误停后续跑。** 监控脚本用 `grep -c "perf N:"` 数轮数，而 GRPO 每轮打印两次（两个 DP 副本），20 行被误判为 20 轮。从 `iter_0000009` checkpoint 带优化器状态续跑补满后 10 轮，第 10→11 轮之间有一次 SGLang 引擎重启。权重和优化器状态连续，但这次重启应在解读时知悉。
2. **SRLVR 臂没有 20 轮的 checkpoint。** `SAVE_INTERVAL=25` 而实际跑了 21 轮，所以该臂只有轨迹数据，没有可供离线评测的权重。GRPO 臂有（`SAVE_INTERVAL=10`）。

## 11. 建议的下一步

### 这组实验回答了什么、没回答什么

**回答了**：ALFWorld 在 4B 和 8B 上已经饱和，SRLVR 和 GRPO 都不再带来提升。这是硬证据，7 条曲线一致。

**没回答**：SRLVR 与 GRPO 的算法差异。因为两臂的任务采样口径不同（32 vs 4 个不同任务/轮），这组数据不足以支撑任何算法优劣的结论。

### 要真正比出算法差异，需要先做两件事之一

1. **对齐采样口径**：GRPO 改成 `bs=32 × G=1`（但那样就没有组，GRPO 退化），或 SRLVR 改成重复采样。前者不成立，所以更现实的是——
2. **离线评测固定测试集**：两臂的 checkpoint 在同一批 held-out 任务上评测，彻底绕开训练时的采样差异。这也是唯一能消除 ±0.05 单轮噪声的办法。

### 任务侧

8B 起点 0.844、剩余空间 0.156、单轮标准差 0.052 —— **ALFWorld 已经不适合作为 8B 的算法评测集**。原规划里的 OSWorld 难度更匹配。

你的 4B 消融（batch 0.793 / history 0.784 / outcome-only 0.744）内部差异 0.05，与单轮标准差 0.08 同量级，同样需要多种子重复才能分辨。

### 更值得看的指标

整体 success_rate 饱和时，这几个仍有区分度：

* **零梯度步占比** —— 8B GRPO 已达 35%，这个指标直接衡量算法在饱和任务上的样本效率
* 达到某成功率所需的 rollout 数（样本效率）
* **难样本子集上的成功率** —— 具体就是那 69 条 50 轮超时轨迹所属的任务族
